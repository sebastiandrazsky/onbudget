# Changelog

Every change users should receive bumps the version (see README, "Development").

## 0.1.2 (2026-10-22)

A session now starts in about 15 to 25 ms however many records the store holds; only the first session start of each day still goes through other sessions' records. No change to anything the model reads or to any budget decision: `tests/e2e/modeltext.py` renders the same 31,396 texts as at `c82a535`.

- Every session start went through the store's budgets and flags of other sessions to delete those older than 30 days, one read each, and a read takes longer the larger the store. With the store a month of normal use leaves (about 780 records, 216 KB) that made each session start take about 130 ms instead of 15; with a heavy month (about 2,600 records, 860 KB), about 0.9 s. Other sessions' budgets and flags are now gone through at the first session start of each day; calibration records, which go by the day in their key at no cost, are still deleted at every start. The store keeps one more value, that day. Now those starts take about 16 ms and 23 ms. Measured on Claude Code 2.1.306 with synthetic stores of those sizes.
- Setting a budget, and `/onbudget`, still read every calibration record once per session to pool the rates: about 0.3 s at a month of normal use, 2.9 s at a heavy month.
- The known issue of 0.1.0 remains: in `claude -p`, set the budget with `ONBUDGET`.

## 0.1.1 (2026-10-21)

A packaging release, with no change to what the plugin does or to anything the model reads: `tests/e2e/modeltext.py` renders the same 31,396 texts as at `c82a535`.

- `eval/` is no longer on `main`, so an install copies 38 files, about half a megabyte, instead of 472 files and 5.5 MB. The evaluation's evidence (the harness, every run's data and the tasks) stays at the tag [`v0.1.0`](https://github.com/sebastiandrazsky/onbudget/tree/v0.1.0/eval) and at `eval-freeze`, `eval-freeze-2` and `eval-freeze-3`, and the documents link there.
- The checks of the evaluation's own tools moved with them, to the tag `v0.1.0` and the development archive: `tests/e2e/dialogs.py` (the smoke script's permission-dialog matcher, 28 checks) and the cap plugin's checks in `run.py` (6) and `wire.py` (2). On `main`, `run.py` has 51 checks and `wire.py` 12 (16 with effortless), and CI no longer runs `dialogs.py`. Every check of onbudget itself is unchanged.
- Listing metadata for the plugin directory: `PRIVACY.md` states what onbudget reads, writes and sends; `.claude-plugin/plugin.json` gains `displayName`, `documentationUrl`, `supportUrl` and `privacyPolicyUrl`, and the keyword `usage-limits` replaces `function-hooks`. The README links to `PRIVACY.md` and says that the store keeps the first line of each budgeted task.
- The known issue of 0.1.0 remains: in `claude -p`, set the budget with `ONBUDGET` (see below).

## 0.1.0 (tagged 2026-10-21)

First version.

- `/onbudget <$X | N% 5h | N% week | 5h | week> <task>` runs a task under a usage budget; `/onbudget` shows the status; `/onbudget off` removes the budget. `ONBUDGET` sets the budget for a headless run.
- Spend is read from the session's own cost ledger, subagents included. Each request is charged its own cost even when requests overlap; the prototype charged a request for everything that ran beside it.
- A request is refused when the spend so far, plus the cost of the dearest request seen for it and for each request still in flight, would reach the budget. The refusal is a visible notice written by the plugin. Two documented ways past the budget remain: one request dearer than any before it, and Claude Code's own requests that do not pass through the model-request hook (the next-prompt suggestion and a compaction).
- Claude sees a one-line meter reading after each tool result and with each follow-up prompt. What it calls "left before the stop" is what the stop rule still allows, with the reserve taken off. The tier turns CRITICAL when two requests' worth or less is left, so a model working one request at a time has read CRITICAL at least twice before a request can be refused, as long as no request costs more than the dearest before it. Effort is capped at medium while a budget is set (configurable).
- While a budget is open, the account's 5-hour and weekly usage windows are limits as well. The meter follows whichever of the budget and the two windows comes first and names the window when it does; the plugin stops with its own notice at 99% of a window (about 97% when it counts the window's points), before Claude Code's limit message would end the session. A budget larger than what a window has left says so when it is set; a window with nothing left refuses the budget in one line, also in a new session, from the last reading seen on the machine.
- `5h` and `week` are budgets: what that window has left below 99% when the budget is set. A reset of the window during the task does not enlarge the budget.
- 5-hour percentage budgets and `5h` are converted to dollars with a rate learned from this account's own usage readings, or enforced on the window reading itself until a rate is known.
- Weekly budgets (`week`, `N% week`) are counted in the weekly window's own whole points unless `usdPerPointWeek` is set, and are good to about a point. The rate learned for the weekly window errs far low (it stood at $3.24 to $3.49 a point, where the evaluation's own spend shows at least $8.50), so converting with it would have stopped a task at about two fifths of the share it named. The learned weekly rate is still used for the weekly limit under dollar and 5-hour budgets.
- Once a budget has stopped a session, further prompts are turned away with the reason, so nothing more is spent on them.
- A status line under the prompt shows the tier, what is left before the stop in its unit, the budget, and the account limit when one binds (`tier MEDIUM · $1.60 left · budget $3.00`; `tier HIGH · $61.16 left (5h limit) · budget $500.00`), in points under a budget counted in points; a stopped budget shows `STOPPED`, the spend against the budget and `/onbudget off`. It is at most 60 characters, so it shows whole in a terminal 77 columns wide or more (Claude Code 2.1.304 to 2.1.306 cut a plugin's status line at the terminal's width), and its most important fields come first. The model never sees it: it reads the longer meter line.
- In a terminal session, when Claude ends the task with its STATUS line, the plugin writes one line of its own: how the task ended, the spend against the budget, how many whole points each usage window moved, and that the budget is still open. Under a budget counted in points it gives the points the window moved against the points budgeted, and the task's own spend in dollars apart. `/onbudget` shows the same points per window. Lines the plugin writes to the transcript carry its name once: Claude Code adds it.
- While a budget is open, Claude Code's own token countdown (`<total_tokens>N tokens left</total_tokens>`, an undocumented figure set by the server and padded to 15 million tokens, which Claude Code 2.1.304 sent with every request in the evaluation) is left out of new requests. This is partial: the copy in the system prompt stays, and its effect on the model was not measured. Nothing already sent changes, and a resumed session gives every countdown the answer it was first sent with. A countdown under a million tokens, or one set with `CLAUDE_CODE_TOTAL_TOKENS_REMINDER`, is kept.
- If another plugin raises a request's effort above the budget's cap (effortless can, depending on load order), onbudget says so once, names the plugin, logs every such request, and shows it in `/onbudget`. It does not try to override it.
- `/onbudget` states the plugin's version and the Claude Code range it was tested on, and says when no usage-window reading has arrived yet.
- The budget survives compaction, a reload, a resumed session and a switch to another session, and ends with `/clear`.
- Requires Claude Code 2.1.287 or later, where plugin mods are on by default. Every suite passed on 2.1.288, 2.1.304 and 2.1.306; earlier builds of this version also on 2.1.289 and 2.1.299.
- A GitHub Actions workflow, with read-only permissions and actions pinned by commit, validates the plugin and runs its in-engine tests, the scripted end-to-end checks and the fake-API checks against the current Claude Code on every push and weekly.
- The evaluation is published with its raw data: `REPORT.md`, [`eval/`](https://github.com/sebastiandrazsky/onbudget/tree/v0.1.0/eval), [`eval/TASKS.md`](https://github.com/sebastiandrazsky/onbudget/blob/v0.1.0/eval/TASKS.md) (each benchmark task's upstream repository, commits and hidden tests), [`eval/rebuild_tasks.py`](https://github.com/sebastiandrazsky/onbudget/blob/v0.1.0/eval/rebuild_tasks.py) (rebuilds the tasks from GitHub and PyPI) and the licence notices of the upstream projects quoted there.
- The paid smoke script [`eval/interactive_smoke.py`](https://github.com/sebastiandrazsky/onbudget/blob/v0.1.0/eval/interactive_smoke.py) now refuses every permission prompt except a create or edit of a file inside its own working folder ([`eval/README.md`](https://github.com/sebastiandrazsky/onbudget/blob/v0.1.0/eval/README.md)).
- The event log is off unless `ONBUDGET_LOG=1`, and goes to one fixed file in the plugin's own folder, `log/events.jsonl` (then `log/events.1.jsonl`, ... every 200 rows); no variable or setting can point it anywhere else. Earlier candidates wrote it wherever `ONBUDGET_LOG` named, which a mistyped value could have aimed at another file.
- The effort cap is set only by the `effort` option (default `medium`, unchanged); the variable `ONBUDGET_EFFORT` of earlier candidates is gone. The remaining variables are `ONBUDGET`, `ONBUDGET_LOG` and Claude Code's own `CLAUDE_CODE_TOTAL_TOKENS_REMINDER`, none of them a secret.
- The README says what the plugin adds to the prompts it submits (rendered from its code and checked by `tests/e2e/readme.py`), what it writes, what each hook does, and why it reads each variable. The plugin has an icon.
- CI installs Claude Code from npm instead of piping an install script into a shell, and also runs `tests/e2e/dialogs.py` (from 0.1.1 those checks live with the evaluation's tools, at the tag `v0.1.0` and in the development archive).

The tag `v0.1.0` first pointed at commit `c82a535`. An acceptance run on 2026-10-21, in real terminal sessions with the real model on Claude Code 2.1.304, found budget enforcement correct and rejected that commit for two display defects: every line the plugin wrote to the transcript began `onbudget: onbudget:`, and the status line put the tier last, where an 80-column terminal cut it off together with the account limit that binds. The release commit fixes both, rewrites the status line and the end-of-task line under budgets counted in points, and corrects the documents; the tag moved once, from `c82a535` to it. What the model receives is byte for byte what it received at `c82a535`: `tests/e2e/modeltext.py` renders it from both commits and compares. A live re-check of the fixes on Claude Code 2.1.306 with Claude Opus 5.5 showed one prefix on the end-of-task line, the 5-hour limit named on the status line, and the end line of a `week` budget in points. The status line through a dollar budget that runs out was seen live up to CRITICAL, but the stop itself was not reached live, because the test driver left a permission prompt open. It is accepted on the stop seen live on 2.1.304 at `c82a535`, whose stop path is unchanged, and on the stop notice and STOPPED line drawn by 2.1.306 with a scripted model.

The directory portal then validated `c3fe8e7` (no Blocks; two warnings and six policy holds, about the event log's path, the environment variables, the README, the icon and the install line in CI). The changes listed in the last four bullets above answer them, and the tag moved once more, from `c3fe8e7` to the new release commit. What the model receives is still byte for byte what it received at `c82a535`.

Known issue in 0.1.0: in `claude -p`, the form `claude -p "/onbudget <budget> <task>"` sets the budget but can exit before the task is sent (exit code 0, nothing run, nothing spent). The plugin submits the task once the command has returned, and the process can end first. Measured: the task was not sent in 1 of 14 CI runs of the end-to-end suite (Linux, Claude Code 2.1.306), and in none of 40 runs of that scenario on macOS (20 on 2.1.304, 20 on 2.1.306). In headless runs, set the budget with `ONBUDGET`. `tests/e2e/run.py` now checks that the task never reaches the model without its budget and that the spend stays within it, and reports a run where the task was not sent as this issue.
